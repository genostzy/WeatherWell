# Barangay flood profile and downstream heads-up Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Officials set their barangay's flood, landslide and storm-surge levels and its downstream barangay; the Hazards layer and every hazard label show them; a first Warning or Evacuate upstream tells the downstream barangay's officials and their town's.

**Architecture:** A `security definer` function writes the profile into `hazard_susceptibility` and `zones`, as `set_barangay_details` writes details. A new public endpoint serves set profiles, and the reference-data provider lays them over the cached data, as it does details, so every `useHazards` reader updates. A trigger on `alerts` writes a `heads_up` row into `official_messages`, and `setZoneAlert` notifies through the existing `notifyOfficialsOfMessage`.

**Tech Stack:** Postgres (Supabase), plpgsql, Next.js 16 (Server Actions, route handlers, `after()`), React 19, Vitest + Testing Library, `supabase/tests/rls.sql` (run in CI).

**Spec:** `docs/superpowers/specs/2026-09-29-flood-profile-and-downstream-heads-up-design.md`

## Global Constraints

- Levels: `low`, `medium`, `high`, `unknown` (shown "Not sure" in the form; `HAZARD_LEVEL_LABEL` elsewhere). Hazards set here: `flood`, `landslide`, `storm_surge`.
- The downstream barangay: another barangay within **20 km** of this one's point, or none.
- The heads-up fires on a new active alert whose severity is `red` (Warning) or `evacuate`, when the alert it replaced (`superseded_severity`) was neither, and the barangay names a downstream one. It reaches **officials only**: the downstream barangay's and their town's.
- Only the barangay's own officials may set its profile (`private.manages_zone`).
- Copy is bilingual (`LocalizedText`) for residents and officials' screens; officials' push and email text is English, as today (`official-recipients.ts`).
- Migrations are applied to the live database with `apply_migration`, files renamed to the reported versions, types regenerated by adding the new entries to `database.types.ts`, and checked once on live in a block that ends in an exception.
- The service worker `VERSION` goes up once per release, in the release commit, not in this plan.
- Commits are authored by the owner alone: no `Co-Authored-By` lines.

## Review Focus

1. A barangay with no `hazard_susceptibility` rows at all (about 11,700 of the 125,409 barangay-hazard pairs have none): saving must create them. Test: FP3 upserts a missing row.
2. An official of barangay A setting B's downstream link, or A's link to a barangay 25 km away: refused. Tests: FP1, FP4.
3. A heads-up for a downstream barangay in another town: `town_code` is the downstream barangay's town, so that town's officials see it. Test: HU4.
4. An old phone that has the details overlay but not the profile endpoint: nothing breaks; the new endpoint is separate. Test: Task 3's provider test with a failing `/api/barangay-profiles`.
5. A Warning set by the town for many barangays at once (`setZoneAlerts`): each barangay's escalation notifies its own downstream officials once. Test: Task 5's `setZoneAlerts` case.

## Rulings made while planning

- **The action record calls it `barangay.profile`**, next to the existing `barangay.details`, where the spec wrote `profile.set`. Cost if wrong: a name.
- **A separate endpoint, `/api/barangay-profiles`**, rather than widening `/api/barangay-details`: phones on the old code keep reading the old shape. Cost if wrong: one more request per app start.
